#### 概要

エンタープライズレベルのテナントが要求するセキュリティ・スケーラビリティを達成するため、KARTE Datahub のリアーキテクチャプロジェクトに従事。権限管理の強化・GUI 改善・API ファースト化を同時推進し、プロダクトの再設計・再構築を行う。アプリケーション・インフラ・認可ポリシーの 3 リポジトリを横断して設計から本番ロールアウトまで一貫して担当。

#### 業務内容

- BigQuery データセキュリティ基盤の設計・実装
  - エンタープライズ顧客が求めるカラム単位・行単位のアクセス制御（CLS / RLS）を、バックエンドから管理画面 UI まで End-to-End で構築し、マルチテナント環境での安全なデータ公開を実現
  - Data Catalog・Firestore・BigQuery Data Policy の 3 システムにまたがる更新処理を Saga パターンで設計。部分失敗時の自動ロールバック・監査ログ保全・IAM 伝播遅延のリトライ吸収を保証し、フォールトインジェクション（障害注入）テストも整備。「画面上は設定済みに見えるがマスキングが効かない」といった無音のデータ不整合を構造的に排除
  - 検証環境で実際に発生した障害を実ログから根本原因まで追跡し、書き込み系 API の冪等化・並行同名作成の「先勝ち + 409」方式・同一テナント内で認証状態が混線する構造的バグなどを恒久修正。対症療法ではなく入力検証・権限変更の共通パターンとして全リソースへ横展開
- 認可ポリシーの Policy-as-Code 化（宣言的な認可基盤の設計・移行）
  - ロール定義・API 操作・GCP IAM 権限・Firestore セキュリティルールがコード上で乖離し、認可バイパスの温床になっていた。この課題に対し、認可ポリシーを YAML で宣言しコンパイラで生成物を導出する仕組みへ移行。ポリシーは不変バージョン付きの成果物として配布し、アプリケーション・Terraform の双方がそれを参照する構成に統一
  - 認可モデルを「ロール → 操作 → 効果 → IAM 付与」の 4 層へ再設計し、108 操作から 146 の効果を生成。ユーザーに払い出すサービスアカウントへの危険な直接権限付与をスキーマ・コンパイラの検証で構造的に拒否し、クレデンシャル漏洩時の認可迂回を防止
  - データプレーン・コントロールプレーン・プロジェクト単位で権限主体を決める IAM 配置原則を ADR として策定。全ドメインの定義監査・実装監査を 24 件の issue に分解して主導し、宣言と実装のズレを体系的に是正
  - ポリシー定義・アプリケーション実装・Terraform 適用の 3 リポジトリにまたがる切り替えを、開発 14 テナント → 評価 9 テナントの順で段階ロールアウト。広範なプロジェクト IAM 管理者ロールを 2 権限のみのカスタムロールへ置き換え、最小権限化を本番運用中のテナントで完遂
  - ロールアウト中に発見した Terraform プロバイダ起因のセキュリティルール一時未適用（切替中に全読み取りが拒否される）を実機で再現し、無停止更新の仕組みを構築。カスタムロール上限到達テナントの部分適用防止・適用中断後の安全な復旧手順も整備
- ロール別サービスアカウントの非同期プロビジョニング基盤の整合性設計
  - テナント内ロールごとに GCP サービスアカウント・カスタムロール・IAM を非同期に構築する仕組みを担当。途中失敗や並行実行によりロールが「有効に見えるが権限が適用されていない」状態に陥る問題を解消。lease と fencing token による書き込み保護を全経路へ適用し、古い試行からの上書きを型レベルで拒否
  - 失敗理由を固定分類で返す status API 契約を新設し、内部エラー文言の外部露出を遮断。ロール削除時の IAM バインディング残留や廃止ロール参照の残存も検出・修復する仕組みを追加
  - 統合テストが GCP カスタムロールの上限（300 件）に到達した障害では、issue の原因仮説を実測で修正（削除後 7 日間のカウント残存と後片付け漏れが主因）。孤児リソース回収と作成量削減で恒久解消
- 公開 REST API 基盤の構築と AI エージェント連携（API ファースト化）
  - 外部システム連携の要望に応えるため、GUI 専用だった機能群を API として開放。社内向け・公開向けあわせて 100 本規模の REST エンドポイントを設計・実装し、クエリ管理から実行・データセキュリティ設定・データ共有までを API 経由で完結可能に
  - OpenAPI スキーマ定義・RFC 9457 準拠のエラーレスポンス・カーソルベースページネーションなど標準仕様に整合した API 設計規約を整備。OAuth スコープによる認可フレームワークを新設し、警告モードから強制モードへの段階的導入により稼働中の API を無停止で認可強化
  - CLS・RLS・クエリ・データ共有の 55 エンドポイントを MCP（Model Context Protocol）ツールとして公開し、AI エージェントから直接呼び出し可能に。OpenAPI 仕様への拡張属性付与だけでツールが生成される運用に整備
  - 同一機能を管理画面・社内 API・公開 API・CLI・MCP の 5 面で揃えて提供する開発様式を確立し、開発者向け CLI にもコマンド群を実装

  - 共有されたデータセットの中身（テーブル一覧・スキーマ・行プレビュー）を、共有元の行・列アクセス制御を適用した状態で確認できる閲覧機能を追加し、外部共有データの透明性を確保
  - 公開に先立ち、鍵なし認証連携経路だけ制限を迂回できる認可バイパスや部分失敗で孤児化した GCP リソースがリトライを塞ぐ問題などを事前に修正し、公開範囲の拡大と安全性を両立

  - ロールプリセットごとの許可・拒否を全 API に対して機械検証する宣言的シナリオテストを 4 系統・516 ステップ新設し、実機で全件パスまで到達。savedQuery の越境実行で監査証跡が無音で欠落する問題や権限エラーの 500 / 200 / 404 への誤分類など、実在する認可穴 7 件を発見し製品コードを修正

  - Clean Architecture への移行を主導し、ドメイン境界の分離・依存性逆転・Protocol Buffer ベースの End-to-End 型安全性を実現。開発速度と品質の両立に寄与
  - レイヤー依存ルールを dependency-cruiser で CI 強制し、全ユースケースをコンストラクタ注入へ統一（約 170 箇所の呼び出し改修）。あわせて循環依存を 94 件から 3 件へ削減し、型チェックや lint が CI を素通りする構造も是正。レビュアーの注意力に依存しない品質担保を仕組み化
- 複数 AI エージェントが並列開発できるローカル環境・CI 基盤の構築
  - 複数の git worktree と AI エージェント（Claude Code / Codex など）を同時起動すると、Compose 名・ポート・ゲートウェイ設定・テストリソースが衝突していた。この課題に対し、worktree ごとに分離した実行レーンと共有ゲートウェイからの振り分けを設計。レーンの採番・付与・回収を一元管理する CLI を整備し、並列開発を標準の開発様式に

  - 実装後は複数の AI レビュアーによる多段階レビューを標準化し、反射型 XSS や全レーン誤削除などの重大バグをマージ前に検出・修正。issue・PR 作成用のスキルやフックも整備し、AI エージェントが背景を知らなくても作業できる文書品質を担保
